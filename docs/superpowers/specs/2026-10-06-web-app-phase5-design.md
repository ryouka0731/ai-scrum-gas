# Web アプリ 第5段階 設計: コメント・議論のスレッド

## 背景

PBI や障害物について話し合う場所が無い。今は説明欄に追記するか、スプレッドシートの「メモ」列に
書くしかなく、誰がいつ書いたかが残らない。本段階で、PBI と障害物にコメントを付けられるようにする。

## 段階の位置づけ

| 段階 | 内容 | 状態 |
|---|---|---|
| 第1〜3段階 | 同期の基盤・PBI の作成編集・タブとビュー | 完了（PR #1〜#3） |
| 第4段階 | 障害物の作成・編集・解決 | 完了（PR #4〜#6） |
| **第5段階（本設計）** | **コメント・議論のスレッド** | 本設計 |
| 第6段階 | 変更履歴と差分表示 | 未着手 |

## 保存先: `scrum/comments.csv`（第1段階の決定を改める）

第1段階の設計書は「コメントはスプレッドシート内のみ。ファイルに戻さない。エージェントはコメントを
読まない前提」とした。**これを改め、`scrum/` の新しいファイルに保存する。**

- その後の段階で「Web アプリは共有スプレッドシートに触れない」「シートは `scrum/` から一方向に
  作り直す控え」が確定した。シートに保存すると、この2つと両立しない
- AI スクラムチームが人のコメント（顧客や PO の声）を読めないのは、スクラムの透明性に反する
- 既存の CSV の列構造は変えない。新しいファイルを足すだけである

列は `id,target_id,author,created_at,body`。

| 列 | 内容 |
|---|---|
| `id` | `CMT-` + 8桁の16進（サーバが `Utilities.getUuid()` から作る）。削除があるので連番にしない |
| `target_id` | `PBI-\d+` か `IMP-\d+` |
| `author` | Web アプリからはログイン中のメールアドレス（`Session.getActiveUser().getEmail()`）。エージェントはエージェント名（例 `scrum-master-kenji`） |
| `created_at` | `YYYY-MM-DD HH:mm:ss`（サーバの時刻） |
| `body` | 本文。1〜2000字。改行可 |

雛形として、ヘッダー行だけのファイルをリポジトリの `scrum/comments.csv` に置き、`publish.js` で配布する。
`publish.js` は、配布先に既にある Web アプリの書き戻し先（この `comments.csv` と PBI・障害物の3つの CSV）を上書きしない。
配布前の Drive にファイルが無いときは、書き込みは「scrum/comments.csv が見つかりません。配布し直してください」
で止まり、読み取りは空として扱う（他の表示を巻き添えにしない）。

## できること

| 操作 | 内容 |
|---|---|
| 読む | PBI のパネル・障害物のパネルの下部に、その対象のコメントを古い順に出す |
| 書く | パネル下部の入力欄から追加する |
| 消す | 自分（同じ `author`）のコメントだけ消せる。確認は挟まず、取り消せる通知で受ける |
| 件数 | 盤面のカードと障害物の一覧に、コメントがあれば件数を出す |

**やらないこと:** 編集、返信の入れ子、メンション、通知、既読管理、シートへの同期。

## 書き込みの手順

- 追加は**追記だけ**なので競合判定は要らない。ロックを取り、読み直したファイルの末尾に足して書く
- 削除は `id` で探し、`author` がログイン中の人と一致するときだけ消す（一致しなければ `forbidden`）
- 削除の取り消しは、消した行をそのまま末尾へ戻す（`id`・`created_at` を保つ）。同じ `id` が既にあれば何もしない
- 書く前にヘッダーを `COMMENT_FIELDS` で検査する（未知の列を消さないため）
- `target_id` は形だけ検査する（`PBI-\d+` / `IMP-\d+`）。対象が今あるかは見ない — 対象が削除されても、
  取り消しで戻ればコメントも見えるように残す

## API

```
apiAddComment(targetId, body)   → { ok, comments, comment }
apiDeleteComment(commentId)     → { ok, comments, removed }
apiRestoreComment(row)          → { ok, comments }
```

- `comments` は `{ <target_id>: [comment, …] }`（全対象。古い順）。パネルと件数の両方がこれを使う
- 読み取りは**専用の API を作らない**。`apiGetView` の `board` / `list` / `impediment` の応答に
  `comments` を載せる。パネルを開くたびの往復が無く、件数も同じ応答から出せる
- 失敗: `{ ok:false, reason, message, comments? }`。`reason` は `busy` / `invalid` / `forbidden` / `not_found` / `error`
- 各コメントには `mine`（ログイン中の人が書いたか）を付けて返す。画面は `mine` のときだけ「削除」を出す。
  判定はサーバでもう一度行う（画面の申告を信じない）

## 画面

- パネル（PBI・障害物の両方）の最下部に「コメント」の節
  - 各コメント: 書いた人（メールの `@` より前）、日時、本文（改行を保つ）。自分のものには「削除」
  - 入力欄（textarea）と「コメントする」。空なら押せない。送信中は塞ぐ
- 新規作成中のパネル（ID がまだ無い）ではコメントの節を出さない
- 応答の順序: コメントの書き込みは対象ごとに独立。応答の `comments` で全体を差し替える。
  別のパネルに移っていたら、そのパネルの表示は差し替えた `comments` から描き直す（応答が古い対象のものでも、
  `comments` は全体なので食い違わない）。書き込みの応答どうしの順序は、障害物と同じく発行番号で新しいものだけ使う

## エージェント（ローカルの Claude Code）

- `CLAUDE.md` に1行足す: 「人のコメントは `scrum/comments.csv`（`target_id` で PBI/障害物に紐づく）。
  PBI や障害物を扱う前に該当コメントを読む。返答を書くときは `author` に自分のエージェント名を入れて追記する」
- スキル（`sprint-review` / `backlog-refinement`）の手順に「該当 PBI のコメントを読む」を1行ずつ足す

## アーキテクチャ

| ファイル | 役割 |
|---|---|
| `scrum/comments.csv`（新） | 雛形（ヘッダー行のみ） |
| `gas/pure_comment.js`（新） | `COMMENT_FIELDS`、検証、追記・削除・戻しの純関数、`groupComments(rows, me)` |
| `gas/pure_write_guard.js` | 許可リストに `comments.csv` |
| `gas/web_app.js` | `withCommentWrite_`、3つの API、ビューの応答に `comments` |
| `gas/kanban.html` | パネルのコメント節、カードと一覧の件数 |

ID の採番はサーバの `Utilities.getUuid()` を使うが、純関数には ID を引数で渡す（テストで固定できるように）。

## テスト

- 純関数: 検証（空・2000字超・`target_id` の形）、追記、本人以外の削除拒否、戻しの冪等、`groupComments` の並びと `mine`
- `web_app_flow`: ファイルが無いときの読み取り（空）と書き込み（案内付きで失敗）、ヘッダー不一致で書かない、
  他人のコメントを消せない、`apiGetView` が `comments` を載せる
- DOM シム: パネルにコメントが出る・追加・自分のものだけ削除が出る・取り消し・新規作成中は節が無い・
  応答の順序（古い応答で戻らない）・件数の表示
- 実ブラウザ: パネルの縦の並び（コメント節で保存ボタンが押せなくならない）

## 実機で確かめること

- 2人のアカウントで、互いのコメントが見え、自分のものだけ消せること
- ローカルの Claude Code が追記したコメントが、再読み込みで出ること
- `comments.csv` を配布する前の Drive で、他の表示が壊れず、書き込みが案内付きで止まること

## 対象外

- コメントの編集、返信の入れ子、メンション、通知、既読
- 共有スプレッドシートへの同期
- 変更履歴と差分表示（第6段階）
