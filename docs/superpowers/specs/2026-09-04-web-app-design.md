# AI Scrum Web アプリ 設計

## 背景

現行の GAS 版は **一方向の可視化** である。`scrum/` のファイルを読み、スプレッドシートに9枚のダッシュボードを再構築する。シート側の編集は次回同期で失われる（メモ列のみ例外）。

しかし本来の想定は次だった。

- **AI のエージェンティックな動きはローカル**（Claude Code がファイルを操作する）
- **それ以外は人がオンラインで操作できる**（Web アプリから）
- **人間は生のスプレッドシートを見ない。** アプリだけを見る
- スプレッドシートはその背後にある DB

本設計は、この構成へ移行するための第1段階を定める。

## 役割の分担

```
[ローカル]                          [オンライン]
Claude Code（エージェンティック）      人間（Web アプリ）
  ↓ ファイル操作                       ↓ 操作
scrum/*.csv  ←────────────────────→  スプレッドシート（DB）
              GAS が双方向に同期
```

生のスプレッドシートは DB であり、人の作業面ではない。人が触るのは Web アプリだけである。

## 段階

| 段階 | 内容 |
|---|---|
| **第1段階（本設計）** | 双方向同期の基盤 + カンバン（ドラッグで状態変更） |
| 第2段階 | PBI の作成・編集フォーム |
| 第3段階 | コメント・議論のスレッド |
| 第4段階 | 変更履歴と差分表示 |

段階を分けるのは、動くものを早く触れるようにして、方向が違えば早く気づけるようにするためである。

## 設計判断

| 論点 | 決定 | 理由 |
|---|---|---|
| UI の置き場所 | GAS の Web アプリ（HTML Service、専用 URL） | カンバンのドラッグやコメントスレッドを自由に作れる。サイドバーでは画面が狭くドラッグに向かない |
| 人の作業面 | Web アプリのみ。生のシートは触らせない | 競合の発生源を1つに絞る。シートは DB として扱う |
| 書き戻しの単位 | PBI 1件ごと（行単位） | ファイル全体を書き直すと、ローカルの並行編集を丸ごと潰す |
| 競合の解決 | `updated_at` による後勝ち + 変更前の値の照合 | CSV に既にある列を使う。照合で「見ていない変更」を検出する |
| Web アプリから `syncAll_()` を呼べるか | 呼べない（第3段階「コメントをシートに保存」に直撃する制約） | (1) `rebuildAllSheets_` の入口が `SpreadsheetApp.getActiveSpreadsheet()` で、Web アプリ実行にはアクティブなシートの束縛が無い。(2) 仮に動いても `syncAll_` は同じスクリプトロックを `tryLock(1000)` で取りに行き、LockService は再入不可なので `skipped:true` を返して黙って何もしない |
| コメント・履歴の保存先 | スプレッドシート内のみ。ファイルに戻さない | CSV の列構造を変えない制約を守る。エージェントはコメントを読まない前提 |

## Drive への書き込み権限

**現在の `oauthScopes` は `drive.readonly` であり、書き戻しができない。**

第1段階で `https://www.googleapis.com/auth/drive` へ広げる必要がある。これは利用者の Drive 全体への読み書きを意味するため、次を守る。

- 書き込み先は `SCRUM_FOLDER_ID` 配下の `scrum/*.csv` に限定する（コード上で親フォルダを検証する）
- 上記以外のパスへは書き込まない
- `README.md` と `docs/setup.md` に、スコープが広がることとその理由、書き込み範囲の限定を明記する

`drive.file` は「アプリが作成したファイル」に限られ、既存の CSV を開けないため使えない。

## アーキテクチャ

### 層の構成（現行の方針を維持する）

- `pure_*.js`: GAS API に依存しない純関数。CSV の生成、行のマージ、競合判定
- `gas_*.js`: `DriveApp` / `SpreadsheetApp` への薄い入出力
- `web_*.js` + `*.html`: Web アプリのエントリポイントとクライアント

判断を伴うロジックは `pure_*.js` に置く。GAS 依存層は自動テストできないためである。

### 第1段階で追加するもの

| ファイル | 責務 |
|---|---|
| `gas/pure_csv_write.js` | オブジェクト配列を CSV 文字列に直す。引用が必要なセルを正しく囲む |
| `gas/pure_merge.js` | 1行の更新を既存の行集合へ適用する。競合を判定する |
| `gas/gas_drive_write.js` | `scrum/` 配下のファイルを書き換える。書き込み先を検証する |
| `gas/web_app.js` | `doGet` と、クライアントから呼ばれる API 関数 |
| `gas/kanban.html` | カンバンの画面。ドラッグで状態を変更する |
| `gas/appsscript.json` | `webapp` の設定と `drive` スコープを追加 |

## 双方向同期の仕様

### 読み取り（既存）

現行の `syncAll_()` をそのまま使う。ファイル → シートの再構築である。

### 書き戻し（新規）

人がカンバンで PBI を動かしたときの流れである。

1. クライアントが `updatePbiStatus(id, newStatus, expectedUpdatedAt)` を呼ぶ
2. サーバが `scrum/product_backlog.csv` を読む
3. 対象 PBI の現在の `updated_at` と `expectedUpdatedAt` を照合する
4. **一致しなければ競合**として拒否し、現在の値を返す。クライアントは画面を更新して再試行を促す
5. 一致すれば `status` と `updated_at` を書き換え、CSV 全体を書き戻す
6. 該当シートを再構築する

`expectedUpdatedAt` は、クライアントが画面を描いた時点の値である。これにより「他の誰か（またはローカルの AI）が先に変えていた」場合に上書きを防ぐ。

### 競合が起きる経路

人はアプリしか見ないため、競合は次の場合に限られる。

- 複数人が同時に同じ PBI を動かした
- ローカルの Claude Code が同じ PBI を変更し、Drive 同期でファイルが更新された

いずれも `updated_at` の照合で検出できる。検出したら**黙って上書きせず、人に見せて選ばせる**。

### Drive 同期のラグ

Drive デスクトップ同期には数秒から数分のラグがある。GAS が読む時点のファイルが、ローカルの最新とは限らない。

これは避けられないため、次で受け止める。

- 書き戻し時に必ず読み直してから照合する（キャッシュしない）
- 競合を検出したら人に見せる
- **ラグの存在をドキュメントに明記する**

### 多重実行の防止

書き戻しは `LockService.getScriptLock()` で直列化する。読み取り専用の `syncAll_()` と、書き込みを伴う API が交差すると、読んだ直後に書かれた内容を上書きしうるためである。

## カンバン画面

### 表示

`product_backlog.csv` の PBI を、`status` ごとの列に並べる。

```
New | Ready | In Progress | Review | Done
```

各カードに表示するもの: PBI ID、タイトル、優先度、サイズ、スプリント。

### 操作

カードを別の列へドラッグすると `status` が変わる。HTML5 のドラッグ&ドロップを使い、外部ライブラリは読み込まない（GAS の Web アプリはサンドボックス内で動き、外部 CDN への依存を増やしたくないため）。

### 反映の見せ方

ドラッグ直後に画面を更新し、サーバの応答を待たない（楽観的更新）。失敗したら元の位置へ戻し、理由を表示する。

競合の場合は「他の変更が先に入っています」と示し、最新の状態を再読み込みする。

## アクセス制御

Web アプリの公開範囲は **「同じ組織内のユーザー」** とする（`webapp.access` を `DOMAIN` に設定）。

実行者は **アクセスしているユーザー自身**（`executeAs: USER_ACCESSING`）とする。`executeAs: USER_DEPLOYING` にすると、URL を開けるドメイン内の誰もが管理者の権限で CSV を書けてしまい、Drive 側の権限制御が一切効かなくなる。`USER_ACCESSING` なら書き込みは各自の Drive 権限で弾かれる（閲覧者は書けない）。

個人の Google アカウントでは `DOMAIN` を選べないため、テナントに応じて `setup.js` が調整する。

## テスト

第1段階で `node --test` により検証するもの。

| 対象 | 確認する内容 |
|---|---|
| CSV 書き出し | カンマ・改行・引用符を含む値が正しく囲まれ、読み直して同じ値になること |
| 行のマージ | 1行の更新が他の行に影響しないこと。列順が保たれること |
| 競合判定 | `updated_at` が一致すれば通し、違えば拒否すること |
| 書き込み先の検証 | `scrum/` 配下以外のパスを拒否すること |

GAS 依存層と HTML は自動テストできないため、実環境での手動確認に委ねる。

## 現行からの変更

- **`oauthScopes` に `drive` を追加する**（読み取り専用から読み書きへ）
- `appsscript.json` に `webapp` の設定を追加する
- `setup.js` が Web アプリのデプロイまで行う
- `README.md` に「人はアプリを見る。スプレッドシートは直接触らない」ことを明記する

## 対象外（第1段階）

- PBI の作成・編集フォーム（第2段階）
- コメント・議論のスレッド（第3段階）
- 変更履歴と差分表示（第4段階）
- `product_backlog.csv` 以外への書き戻し
- スプリントバックログや障害物ログの編集
