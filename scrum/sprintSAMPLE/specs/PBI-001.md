## なぜ
利用者がチケットの全体状況を素早く把握できないと、対応漏れや優先度判断の誤りが起きる。
一覧画面で状態を可視化し、日々の運用判断を支える。

## スコープ（やること）
- チケットを一覧表示する画面
- ステータス（未着手/対応中/完了）でのフィルタ
- 作成日時での並び替え

## Non-goals（やらないこと）
- チケットの新規作成・編集（別PBIで扱う）
- 通知・メール連携
- 権限管理

## 受入基準
| # | 基準 | DoD対応 | 判定 |
|---|------|---------|------|
| AC-1 | 一覧に id / タイトル / ステータス / 作成日時 が表示される | 9-1, 9-2 | はい / いいえ |
| AC-2 | ステータスで絞り込むと該当チケットのみ表示される | 9-1 | はい / いいえ |
| AC-3 | 作成日時の昇順/降順で並び替えできる | 9-1 | はい / いいえ |

## インターフェース / データ
- 画面: `/tickets` 一覧ページ（テーブル表示、フィルタUI、ソートUI）
- API: `GET /api/tickets?status=&sort=` → チケット配列を返す
  - status の正規値: `not_started`（未着手）/ `in_progress`（対応中）/ `done`（完了）。画面はラベル表示、API・DBは正規値を用いる
- データ構造: ticket { id, title, status, created_at }（status は上記正規値）

## 検証方法
- `/tickets` を開き AC-1〜AC-3 を手動確認する
- API を `curl "http://localhost:3000/api/tickets?status=in_progress&sort=created_at.desc"` で確認する

## 依存・リスク
- 依存: チケットのデータモデル（DBスキーマ）が先に存在すること
- リスク: 件数増加時の表示性能。→ ページングは後続PBIで検討（Non-goals）
